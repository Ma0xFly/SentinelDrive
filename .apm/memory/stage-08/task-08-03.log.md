# Task 8.3 - AI 来源规范化接入

## Summary

Worker 规范化管道已能识别外部/AI 写入的 raw 情报（`source_type="api"` + `metadata.entry_origin="external_ingest"`），并用与后端 ingest API 完全一致的去重键规范化，保证幂等、与内联 ingest 记录收敛到同一核心情报行。

## Details

任务在 `feat/external-ingest-normalization` 分支完成，提交为 `79fd4d3`。先读取了依赖方 Backend Agent 的 ingest 产物（`intelligence_ingest.py`、`schemas/intelligence.py`、`routes/intelligence.py`）与本仓库的规范化面（`normalizers.py`、`registry.py`、`dedup.py`、`models.py`、`service.py`、`test_normalization_pipeline.py`）。

实现要点：

- 在 `dedup.py` 新增 `external_ingest_dedup_key`，逐字复刻后端 `_dedup_key` 的优先级与字符串格式：`cve → external(dedup_key) → external(external_id) → content → url → text`，哈希复用了与后端 `_stable_hash` 字节等价的 `stable_hash`。
- 在 `normalizers.py` 新增 `ExternalIngestNormalizer`，复用 `BaseNormalizer`，并显式覆盖 `dedup_key`（类比 `ManualNormalizer`）。幂等分支类比 `ManualNormalizer`：当 `entry_origin=="external_ingest"` 且记录已 normalized 时 raise `NormalizationError`。
- 字段映射：`cve_id`（metadata 显式值优先，否则 `find_cve` 从 external_id/title/summary/source_url 推导）、`external_id`、`severity`、`affected_vendor`、`affected_product`（取 `affected_products` 首项）、`vehicle_component`（由 `components` 推断）、`attack_surface`（由 `attack_surfaces` 推断）、`external_score → risk_score`、`risk_level`（由 severity 映射）、tags（`external_ingest` + platform + components + attack_surfaces）、`external_ids`（external_id/cve_id/cnvd_id/vendor_advisory_id/dedup_key/content_hash），保留 `SourceAttribution` 来源归因。
- 在 `registry.py` 增加 `entry_origin` 解析维度，`resolve` 顺序为 `source_name → entry_origin → source_type`，并注册 `entry_origin="external_ingest"` 到新 normalizer。既有 `nvd`/`cisa-kev`/`rss`/`vendor-advisories`/`manual` 解析路径不变（`source_type="api"` 无 external_ingest 标记时仍回落 `FallbackNormalizer`）。

未做任何 schema 迁移，未引入 AI 分析、自定义评分规则、工单流或新通知渠道。

## Important Findings

- 后端 ingest 写入的 raw 行并不在 `metadata` 中保留 `cve_id`、`external_id`、`dedup_key`、`severity`、`affected_vendor`、`external_score`：`external_id` 列折叠了 `external_id or dedup_key or cve_id`，`content_hash` 列合并了显式值与派生值且无区分标记。因此 worker 的 `ExternalIngestNormalizer` 只能对 `cve_id` 做推导（`find_cve`）并把其余字段当作可选 metadata。当前后端写入的 raw 行是 `processing_status="normalized"`，worker 的 pending 查询不会处理它们；未来若新增把外部/AI 情报写成 pending raw 的 connector，需在 `metadata` 中显式写入 `cve_id`/`external_id`/`dedup_key`/`severity`/`affected_vendor`/`external_score` 才能与 ingest 完全对齐这些字段。
- 仓库存在 `worker/app`（Celery 应用包）与 `backend/app`（FastAPI 应用包）同名模块冲突。交叉收敛测试通过 pytest 的 `pythonpath = backend worker`（backend 在前）才将 `import app` 解析到后端；若调整该顺序会引入歧义。
