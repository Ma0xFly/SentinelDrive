# Stage 7 Task 1 - Automated Processing Pipeline

## Summary

Implemented an automated worker processing pipeline that runs source collection, raw persistence, normalization, and scoring in one retryable/idempotent orchestration path. Scheduled Celery Beat now invokes `sentineldrive.process_pipeline` instead of the collection-only sync task, while `sentineldrive.sync_sources`, `sentineldrive.normalize_raw_intelligence`, and `sentineldrive.score_threat_intelligence` remain available for focused operations.

Added operator scripts for a full one-shot processing run:

- `worker/scripts/process-once.sh` runs the worker pipeline synchronously.
- `backend/scripts/evaluate-alerts.sh` runs backend alert evaluation from the backend package.
- `scripts/process-once.sh` and `make process-once` run worker processing first, then backend alert evaluation.

## Implementation Notes

- Added `worker/sentineldrive_worker/pipeline.py` with structured per-stage results and top-level counts for sources seen/succeeded/failed/skipped, raw created/updated, normalization rows, scoring rows, alert evaluation, and stage failures.
- Added `sentineldrive.process_pipeline` Celery task in `worker/app/tasks.py`.
- Updated worker Beat schedule in `worker/app/celery_app.py` to schedule full processing on `SOURCE_SYNC_INTERVAL_SECONDS`.
- Added `worker/sentineldrive_worker/process_once.py` for synchronous script execution and JSON output.
- Added backend alert evaluation script module `backend/app/scripts/evaluate_alerts.py` plus shell wrapper.
- Updated operational, connector, environment, development, scaffold, and testing documentation for collection-only vs full processing behavior.

## Important Findings

Direct worker-side reuse of backend alert evaluation is not safely integrated in the current packaging. The backend alert service depends on backend ORM models and package layout, while the worker image copies only the worker package and scripts. Importing backend alert evaluation from the worker would couple the worker image to backend internals and break the existing service boundary.

The implemented full operator path therefore runs alerts from the backend service after the worker pipeline completes. The worker pipeline exposes an injectable alert evaluator seam for tests and future packaging changes, but defaults to a structured skipped alert stage with reason `backend_alert_evaluation_not_imported_by_worker`.
