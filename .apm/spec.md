# APM 规格说明

## 项目概览

SentinelDrive 是面向中国车联网安全研究与安全运营的威胁情报平台。系统需要持续运行，采集公开情报和人工录入情报，将其规范化到车联网领域数据模型，合并重复或相关情报，支持搜索与筛选，计算风险评分，并生成基础告警。

MVP 交付目标是一个可在单台 Ubuntu 服务器上运行的完整 Docker Compose Web 平台，包含后端 API、定时采集、后台 Worker、PostgreSQL、Redis、中文前端工作台和运维文档。项目成功标准是：平台能够采集已批准的数据源，持久化原始情报和规范化情报，避免同一 CVE 生成重复核心记录，提供可用的搜索、详情和告警视图，并允许后续通过 Connector 模式新增数据源，而不改动核心业务逻辑。

## 工作区

工作区根目录为 `/home/myx/SentinelDrive`。项目最初包含 APM 规划脚手架（`.apm/`、`.agents/`、`.codex/`）和权威产品需求文档 `需求.md`。实现工作应以当前仓库实际文件为准，不假设存在隐藏约定或未发现的业务代码。

---

> **说明：** `需求.md` 是权威需求来源，应在实现字段、业务术语、里程碑意图和验收标准时优先参考。规划和实现必须考虑目标服务器约束：Ubuntu 22.04、4 核 CPU、4 GB 内存、40 GB SSD、3 Mbps 带宽和 300 GB/月流量。

## 权威需求来源

`需求.md` 定义了项目定位、MVP 数据源清单、业务流程、数据模型字段、风险评分因素、告警触发器、前端页面、部署目标、非功能需求、里程碑意图和验收标准。本 Spec 记录对实现有约束力的设计决策和已澄清范围。如果某个需求细节没有在本文重复描述，则以 `需求.md` 对应章节为准；如与本文明确决策冲突，以本文决策为准。

## 产品范围

MVP 是一个可运行的 Web 平台，不只是后端服务或数据管道。必须包含：

- 后端 API 服务。
- 定时采集服务。
- 后台 Worker 服务。
- PostgreSQL 持久化。
- Redis 队列与缓存支持。
- 中文前端工作台。
- 反向代理配置模板。
- Docker Compose 部署。
- 开发文档和运维文档。

MVP 面向个人或小团队使用。系统必须初始化单个管理员账号，并支持创建额外用户，但不得实现复杂多租户或细粒度角色权限系统。

MVP 不包含：暗网采集、知识图谱、AI 自动分析、攻击链生成、工单流程、商业化多租户权限、GitHub API 集成、海外采集节点、自定义风险评分规则、恶意样本分析、车辆远程控制、车端 IDS 和实时 CAN 总线检测。

## 技术栈

已批准的 MVP 技术栈如下：

| 关注点 | 决策 |
| --- | --- |
| 后端 API | FastAPI |
| Worker 与任务 | Python Worker + Celery |
| 调度 | Celery Beat |
| 数据库 | PostgreSQL |
| 队列/缓存 | Redis |
| 搜索 | MVP 使用 PostgreSQL 全文搜索 |
| 前端 | Next.js / React |
| 部署 | Ubuntu 22.04 上的 Docker Compose |
| 反向代理 | Caddy 或 Nginx 配置模板 |

PostgreSQL 全文搜索是 MVP 起点。架构必须为后续接入 Meilisearch 或 OpenSearch 留出空间，但不得强迫 MVP 运行额外的高内存搜索服务。

Celery 是首选 Worker 基础，因为平台后续需要支持多个 Worker 节点和队列化执行。实现时不要假设永远只有一个本地进程执行调度或采集工作。

## 数据源 Connector 架构

采集必须采用 Source Adapter / Connector 模型。每个数据源实现为独立 Connector，负责数据源配置、拉取、源特定解析、限速、重试、错误处理、原始元数据捕获、来源归因、增量同步状态，以及输出稳定的 Raw Intelligence 结构。

新增普通数据源时，核心存储、规范化、去重、搜索、评分和告警逻辑不应需要修改。新增 RSS 源应通过配置完成，不改核心代码。新增 API 型数据源可以增加新的 Connector，但不应修改数据库核心模型。

Connector 行为必须支持配置启用/停用、同步间隔、超时、限速、重试策略，以及源特定凭证或请求头。密钥必须通过环境变量或预留密钥管理能力的配置层提供，绝不能硬编码。

## MVP 情报源

MVP 必须支持以下数据源类型：

| 数据源 | MVP 决策 |
| --- | --- |
| NVD CVE | 必需。使用 NVD API 2.0，支持可选 API key，默认首轮同步最近 120 天窗口，并支持后续回填。 |
| CISA KEV | 必需。使用官方 JSON/CSV 数据源或受维护的官方镜像。 |
| RSS | 必需。支持安全博客、研究团队和厂商安全中心的可配置 Feed。 |
| 人工录入 | 必需。支持用户录入漏洞、公告、事件、暴露面和研究线索。 |
| 厂商公告 | 必需，采用代表性覆盖。首批包含：比亚迪、蔚来、理想、高通、博世。厂商页面可作为源特定 Connector 或可配置公告端点处理；当页面无法稳定机器解析时，保留人工友好的兜底方式。 |

厂商公告支持不能承诺对所有页面格式实现完美自动解析。MVP 应采集和跟踪代表性官方公告或漏洞披露入口，保留链接和元数据，并在存在结构化或半结构化内容时进行规范化。

NVD 必须在没有 API key 时也能运行，但使用更严格的限速。如果配置了 API key，应通过配置启用以提高吞吐。默认 NVD 同步不能在首次启动时尝试导入完整历史 CVE。

## 数据生命周期

核心流程如下：

```text
Source Connector -> Raw Intelligence -> Normalize -> Deduplicate -> Threat Intelligence -> Search / Score / Alert
```

Raw Intelligence 保留采集证据并支持重新处理。Threat Intelligence 是供搜索、评分、告警和前端视图使用的规范化业务对象。两类对象的详细字段要求见 `需求.md`，尤其是 Raw Intelligence 和 Threat Intelligence 章节。

实现至少需要支持以下规范化情报类型：

- 漏洞。
- 暴露面。
- 事件。
- 公告。

车联网领域字段是核心业务字段，不是装饰性字段。规范化记录应支持车辆组件和攻击面分类，例如 App、T-Box、IVI、OTA、V2X、Charging、Cloud API、Bluetooth、Wi-Fi、Cellular、CAN 和 USB。

## 原始内容留存

MVP 必须采用轻量原始内容留存策略，因为目标服务器只有 40 GB 磁盘且带宽有限：

- API 和 RSS 响应在体积合理时可存储结构化原始 JSON/XML 内容。
- HTML 页面默认不保存完整快照。保存源 URL、标题、摘要或提取文本片段、内容哈希、抓取时间、HTTP 元数据和解析状态。
- PDF 文件和附件默认不下载。只保存链接和元数据。
- 采集日志和任务历史应支持可配置留存，默认范围为 30 到 90 天。
- 如果后续需要完整快照或附件，设计应预留对象存储扩展空间。

## 规范化与去重

规范化负责将源特定 payload 映射到共享 Threat Intelligence 模型。每条规范化记录必须保留来源名称和来源 URL，使用户能追溯证据到原始来源。

去重必须采用分层策略：

- 存在 CVE ID 时优先使用 CVE ID。
- 规范化源 URL。
- 标题与来源组合。
- 内容哈希或规范化文本哈希。
- 可用时使用源特定外部 ID。

同一个 CVE 不应创建多个独立核心 Threat Intelligence 记录。多个来源反复命中同一情报时，应合并来源归因，更新 `last_seen_at`，并支持“多来源重复出现”的告警逻辑。

## 风险评分

MVP 风险评分使用固定规则，不使用 AI，也不支持用户自定义规则。评分结果必须包含数值型 `risk_score` 和风险等级：

| 等级 | 范围 | 含义 |
| --- | --- | --- |
| Critical | 90-100 | 高严重性、已知被利用，或可能影响车辆安全与关键车辆操作。 |
| High | 70-89 | 影响范围广或存在清晰利用路径。 |
| Medium | 40-69 | 存在明确安全影响，但利用条件更高或确定性较低。 |
| Low | 0-39 | 影响有限或信息不足。 |

规则因素必须包含 CVSS 分数、是否进入 CISA KEV、可用时的公开 PoC 信号、远程可利用性、认证要求、是否影响车辆关键组件、是否关联远程控制/定位/OTA/车门/启动/充电/车内网络、多厂商或通用组件影响，以及来源可信度。

规则必须透明且可测试。每个因素都应能从已存储字段或明确来源信号追溯，使分析人员理解评分原因。

## 告警

MVP 必须为高优先级情况生成基础告警记录：

- 新增 Critical 情报。
- 新增 CISA KEV 漏洞。
- 影响 T-Box、OTA、Cloud API、远程 App 控制、CAN、V2X 或 Charging 的高风险情报。
- 同一 CVE 被多个来源观察到。
- 短时间内同一厂商或组件出现多条高风险情报。

告警必须保存标题、关联情报 ID、触发规则、风险等级、触发时间、当前状态和备注。告警状态更新必须可审计。MVP 告警不要求外部通知渠道，例如邮件、飞书、企业微信、Telegram 或 Slack。

## 搜索、筛选与导出

搜索和筛选必须支持 `需求.md` 中的主要分析流程：CVE、厂商、产品、组件、攻击面、风险等级、标签、来源和状态。MVP 使用 PostgreSQL 全文搜索即可，但 schema 和服务边界应允许后续替换或增强为专用搜索引擎。

MVP 导出范围：

- 情报列表导出为 CSV。
- 单条情报详情导出为 Markdown。
- 告警列表导出为 CSV。
- 单条情报或告警摘要生成基础 PDF 报告。

导出必须遵守认证要求，避免包含密钥、Token、私有凭证或不应在前端展示的敏感原始数据。

## 前端工作台

前端必须是中文安全运营工作台，不是营销站点。必需页面：

- 情报列表：支持搜索、筛选、排序，并展示风险与状态。
- 情报详情：展示来源链接、摘要、影响对象、车联网领域分类、评分解释和关联告警。
- 告警列表：展示风险、触发规则、状态，并支持状态更新流程。
- 数据源管理/状态页：展示启用状态、最近同步时间、失败次数和最近错误。
- 人工录入页：支持录入漏洞、公告、事件、暴露面或研究线索。

界面应优先保证可扫描性、适中的信息密度、可预测导航和清晰的运营动作。

## 安全与合规

管理工作台必须要求登录。密码、API Token、NVD key、数据库密码和其他密钥不得硬编码。Docker Compose 部署中，数据库、Redis 和未来搜索服务不得暴露到公网。

服务器层面只应暴露 SSH、HTTP 和 HTTPS。Compose 部署应包含反向代理模板，域名和证书配置在部署时处理。

采集器必须使用合理限速，并尊重目标站点条款与可接受访问频率。平台不得在前端展示未脱敏的私有数据，例如凭证、Token、批量 VIN 数据或车主个人数据。

操作日志必须记录关键用户动作，例如人工录入、状态变更和告警关闭。必须保留来源 URL 和抓取时间，以支持审计。

## 部署与演进

MVP 部署目标是单台 Ubuntu 22.04 服务器，使用 Docker Compose，并包含这些服务：

- frontend。
- backend。
- scheduler。
- worker。
- postgres。
- redis。
- reverse-proxy。

设计必须避免强绑定单节点假设。后续应能迁移 PostgreSQL 到托管数据库、Redis 到托管队列/缓存、原始快照到对象存储、Worker 到多节点，最终也应能迁移到 Kubernetes。

资源使用必须贴合目标服务器约束。MVP 避免不必要的重型依赖。后台工作应限速、可恢复、相互隔离，确保单个 Connector 失败不会导致整个平台不可用。

## 文档要求

交付项目必须包含：

- 本地开发 README。
- Ubuntu Docker Compose 部署指南。
- 环境变量参考。
- Connector 开发指南。
- 启动、停止、查看日志、运行迁移、触发同步等运维命令。
- PostgreSQL 与相关持久化数据的备份和恢复指导。

文档必须实用、命令导向，面向需要在目标服务器上启动 MVP 的开发者或运维人员。
